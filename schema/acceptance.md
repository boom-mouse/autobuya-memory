# 入库验收规范

案例不是“记录了一次操作”，而是“未来还能复用的根因知识”。不满足门槛时不要硬凑。

借鉴成熟 lessons log 与 memory 类 skill 的共识：案例要能独立阅读、标题面向未来检索、一条案例只讲一条主根因、普通修缮不要强行写成知识。

## 入库门槛

同时满足以下条件才写入：

- 根因可解释：能说明为什么发生，而不是“换了个写法就好了”。
- 现象可辨认：只看一行 `symptom` 或错误签名，就能判断是否遇到同类问题。
- 修复可迁移：`fix` 能压缩成一句话规则，并应用到其他包或后续审查。
- 未来会再遇到：属于改包、验收、视觉、功能、构建或交付中的常见问题。
- 已查重：同一根因已有案例时，追加到既有案例，不新建重复条目。
- 可独立阅读：不依赖某个会话、某个包内部上下文；未来的人或 agent 只看这一篇就能理解并判断是否适用。

## 不该沉淀

- 没有定位的猜测。
- 只有一次性手工操作，无法归纳成规则。
- 平凡改动但说不出为什么，例如单纯换配置、重命名、格式整理。
- 一个大案例塞多个不相关根因。
- 只写“改了某文件某行”，没写为什么。
- 含客户、用户、证书、密钥等敏感信息。
- 标题和 tags 只依赖项目名、包名、文件名，离开本项目就搜不到。

## 检索颗粒度

标题、symptom、tags 必须用“换一个项目也能搜到”的通用词：

- 好：`深色模式弹窗文字与背景同色`
- 差：`XX 包 1021 问题`
- 好 tag：`深色模式、弹窗、主题色`
- 差 tag：`项目A、周五修复、那个bug`

一条案例一个根因。不要把“弹窗深色模式”、“列表卡顿”、“构建失败”写进同一个文件。

一条案例只留一条主教训。不要为了“显得有收获”堆三条感悟；没有真实根因时明确不沉淀。

复盘优先写给未来的人“下次怎么做”，而不是只有“这个项目不可以怎么做”。在适用边界里说明哪些场景会触发、哪些场景不适用。

## 检索友好度

- `symptom` 写用户可见表现，不要只写内部缩写。
- `error_signatures` 写日志原文、错误码、异常签名。
- `fix` 必须是一句话，能直接出现在下次检索结果里。
- `tags` 至少 2-3 个通用词，并尽量带上同义词，例如：溢出/遮挡/重叠、闪退/崩溃/黑屏。
- 具体项目、版本、文件路径可放正文，但不要作为检索主入口。

## 提交前自检

写入并推送前，逐项检查：

- [ ] 根因已定位，不是猜测。
- [ ] 一条案例只对应一个根因。
- [ ] `title` 或 `symptom` 能通过 2 字通用中文词搜到。
- [ ] `fix` 是一句话可复用修复。
- [ ] `tags` 带通用词和同义词。
- [ ] 已查重，同根因案例已合并。
- [ ] 已脱敏，无客户/个人/密钥信息。

任一项不满足：先补全或修改；无法补全时不要推送。
